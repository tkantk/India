# Namaste India — Plan 3: Make It Work, Then Make It Beautiful

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Fix what the first real-device test exposed, in that order — everything that makes the site *not work* before anything that makes it *look better* — and build each fix as the component the remaining 32 states will reuse.

**Architecture:** No new subsystems. Every fix lands in code that already exists: the narration engine, the cue/timings pipeline, the map layers, the layout shell. The one new dataset is a neighbouring-landmass polygon for the ocean, and the one new component is the landmark photo view, which is written for Plan 4's state screens and merely *used* by the tour.

**Tech Stack:** Unchanged. React 19, Vite, TypeScript, `motion` 13.1.1 from `motion/react`, Vitest.

---

## Why this plan exists

The site went live and was tested on an iPad with the child it was built for. It did not go well, and the verdict was specific:

> *"it looks a bit bland and the initial screen is also bad and the India map towards the down is overlapping with text… around the map it should show blue ocean but not showing that. It also says that trace the map with fingers but does not allow that, its confusing. The Delhi showing is very bad the images are fake… Also stopping and pausing is difficult… in between the tone of the narrator changes… the tiger goes off the screen but the voice is still talking about it. It happens with all of them."*

Five investigations established the causes by measurement. The findings are quoted throughout with their numbers, because several are counter-intuitive and one contradicts what the code's own comments claim.

**The instruction that orders this plan:** make it work properly first, then make it beautiful. And keep it reusable for the states that come next.

## Global Constraints

Every task's requirements implicitly include this section.

### Carried forward, unchanged

- Node 23+, ESM. `erasableSyntaxOnly`: no enums, namespaces, or constructor parameter properties. No Node APIs in `src/`.
- `motion` from `motion/react` only. `useReducedMotionConfig()`, never `useReducedMotion()`.
- Never a leading-slash asset path. Vite `base: './'` with `HashRouter`.
- **Never transform an SVG `<g>`; never animate `viewBox` frame by frame.** WebKit's legacy SVG engine cannot composite SVG children. The camera is a CSS transform on the HTML `.stage`, committed to `viewBox` in one frame.
- **No SVG `<filter>` anywhere.** WebKit blurs on the CPU in three passes.
- Touch targets 104 CSS px for anything the child taps. Every control carries a word.
- **A test double must be faithful to the real interface it stands in for.**
- **jsdom does no hit testing and no layout.** Any claim about real browser behaviour needs a real browser. A listener on a `pointer-events: none` element never fires, and no unit test can see it.
- Nothing on the cue or beat path may throw.

### New, and specific to this plan

- **Evidence before repair, for the audio.** Four distinct WebKit bugs produce the reported symptom and each needs a different fix. Task 1 exists to find out which one fired. Do not implement a repair for a bug that has not been shown to be the one happening.
- **`ctx.state` is not a liveness signal.** WebKit sets it asynchronously from a completion callback, so a synchronous read after `await ctx.resume()` returns the pre-transition value. Worse, the real failures report `state === "running"` with `currentTime` frozen. **Liveness means `ctx.currentTime` advancing**, and nothing else.
- **Never `await ctx.resume()` bare.** WebKit bug 281566: the promise can neither resolve nor reject. Always `Promise.race` it against a timeout.
- **The child must never reach a state with no way out.** No screen may remove its own escape. The control bar is never replaced.
- **No visual duration may be a hardcoded constant when the audio can supply it.** Three such constants are already provably stale against the current render. The per-verb constants stay in the source as *fallbacks* for the paths where no timing exists — the draft-voice pipeline and single-effect tests — but nothing may prefer a constant over a derived value that is available. Keeping the fallback is required by Task 3, not a violation of this rule.
- **Build for the state screens.** Every component this plan touches will be reused by 32 more places. If a fix only works for the tour, it is the wrong fix.

### Task 2: Make audio transport reliable

**Files:**
- Modify: `src/audio/Narrator.ts`, `src/ui/Controls.tsx`, `src/tour/GrandTour.tsx`
- Test: `src/audio/Narrator.test.ts`, `src/ui/Controls.test.tsx`

**Interfaces:**
- `resumeContext()` is replaced by `recover(): Promise<boolean>` — single-flight, proves liveness rather than sampling state.
- The engine gains `wantPlaying: boolean` — the child's *intent*, distinct from whether a node happens to be running.
- `stuck` keeps its meaning but is set only after recovery has genuinely failed.

**The eight defects, in the order they should be fixed.** Every one was established by reading WebKit's source or its bug tracker; none is speculative.

**2a — `playing` lies to React.** `startFrom()` never calls `emit()`, so `resume()` flips `playing` false→true with no notification. The bar keeps reading "Play" while audio runs, and the next tap pauses instead of resuming. *This alone is very likely the literal cause of "stopping and pausing is difficult", independent of everything else.* Call `emit()` at the end of `startFrom` and `stopSource`. **Do this first — it is small, and it may be most of the reported problem.**

**2b — the liveness probe.** Add to `tick()`: while `this.src` is non-null, compare `ctx.currentTime` advance against `performance.now()` advance. If wall time advances ~500ms while the audio clock does not, the context is wedged *despite reporting running*. This is the only thing that can see bugs 263627, 276687 and 283419. Ignore any interval spanning a `document.hidden` period — rAF is throttled when backgrounded and would report a false freeze on every return.

**2c — `recover()`.** Replace state-sampling with:
1. If `running` and `currentTime` advances across ~120ms, return true.
2. `await Promise.race([ctx.resume(), timeout(1000)])` — never a bare await.
3. If still not live: `await ctx.suspend(); await sleep(250); await Promise.race([ctx.resume(), timeout(1000)])`.
4. Wait up to ~1s for `currentTime` to actually advance. Only then `setStuck(true)`.

Single-flight, so the three callers cannot stack repairs. **Step 3 must never bail before its resume runs** — `suspend()` sets WebKit's `m_wasSuspendedByScript`, which disables WebKit's own auto-resume until JS resumes, so an early return converts a transient interruption into a permanent one.

**2d — one rule for `statechange`.** `running` clears `stuck`; anything else, while we believe we should be playing, schedules a `recover()`. Delete the `interrupted`-only branch: WebKit chooses between Interrupted and Suspended for the *same physical event*, so the current asymmetry is nondeterministic and the ignored branch leaves `stuck` true forever. Fix the comment claiming `interrupted` is absent from the enum — it is in the editor's draft and on MDN.

**2e — `play()` must not block on recovery.** Line 201's `await this.resumeContext()` means one never-settling promise freezes all fourteen beats: no clip, no `onEnd`, no advance, a map that simply stops talking. Fire-and-forget `void this.recover()`; the fetch and decode below do not need a running context. Gate only `startFrom` on liveness.

**2f — never start a node against a frozen clock.** `startFrom` records `startedAt` from `ctx.currentTime`; if that clock is frozen, `position` never advances, no cue or word fires, `onended` never arrives, and the tour hangs with `playing === true`. Bail and mark for retry if not running. `resume()` and `replay()` become async and `await recover()` first — **but their callers must stay synchronous at the tap boundary**, starting the async work before the first await, exactly as `StartGate.begin` already does, or iOS discards the gesture.

**2g — honour a pause that lands mid-load.** `pause()` returns immediately when `!this.src`, so a pause during `play()`'s fetch/decode window is silently dropped and the beat starts anyway. The new `wantPlaying` flag fixes this. Teach `GrandTour`'s `if (!n.playing) advance()` to distinguish "nothing to play" from "deliberately paused", or a pause during a load skips the beat.

**2h — release the buffer.** `stopSource()` disconnects but never clears `s.buffer`. Every pause, resume, rate change and replay leaks a node pinning a decoded AudioBuffer, which WebKit holds for about a minute past its last reference (bug 189337) and which killed Safari after ~12 cycles on an iPad 5 (bug 230192). Add `try { s.buffer = null } catch {}` after `disconnect()`, in `stopSource`, `stopAmbient` and both `onended` handlers.

**2i — delete the dead end.** `Controls` currently replaces the *entire* toolbar, Home included, with one button whose handler only calls `resumeContext()` and never restarts narration. Keep all five buttons always. Show a non-blocking banner above the bar, and in the engine arm a **one-shot, capture-phase** `document` `pointerdown` that calls `recover()` and, if `wantPlaying`, resumes. Any tap anywhere heals it; Home is always reachable.

**2j — `visibilitychange` must not render a verdict.** It may attempt recovery but must never `setStuck(true)`: iOS will not grant a resume outside a gesture, so a background flick currently paints a permanent-looking dead end over healthy audio. If recovery does not take, arm the gesture listener instead of showing anything.

### Task 3: Make the art stay while the voice is still talking about it

**Files:**
- Modify: `scripts/lib/words.mjs` (`cueTimes`), `src/types.ts`, `src/tour/cues.ts`, `src/tour/overlays.tsx`, `src/tour/GrandTour.tsx`, and eight files under `src/tour/effects/`
- Test: `scripts/lib/words.test.mjs`, `src/tour/overlays.test.tsx`

**The defect.** Every hold is a hardcoded per-verb constant in `Reveal.tsx` — `HOLD.symbol = 6000`, sea 7000, outline 9000, river 9000, mountains 9000, script 8000, counter 5000, flag 12000, here 5600 — mirrored again in `GrandTour.tsx:stageHold()` for Mor. Nothing in that path ever consults the clip's duration or the next cue's time.

The docstring in `Reveal.tsx` justifying the constants says *"Every one of them is cut short in practice by the next cue."* **That is false for every non-accumulating cue in the current data.** Not one is truncated by a following art cue.

**Interfaces:**
- `cueTimes(cues, timings, duration)` gains a third argument and emits `hold` (ms) on art cues:
  `hold = clamp(min(nextIndependentArtCue.t, duration) - t, MIN_HOLD, CAP[verb])`
- "Independent" excludes members of an accumulating group — `showScript` versus `showScript`, and any two of the three seas — because those restart one instance rather than replacing it.
- Non-art verbs (`playSfx`, `highlightAllStates`, `highlightUnionTerritories`, `highlightState`, `lightNeighbour`) get no hold.
- **`zoomTo` IS an art verb** and this is the easy mistake in the whole task — it looks like pure camera work, but it also raises the "look down" ring at the end of the flight, which is what `HOLD.here` times. Classify it as art or beat 5 keeps its bug. The complete art set in `content/tour.json` is: `revealSymbol`, `showScript`, `countTo`, `unfurlFlag`, `traceRiver`, `raiseMountains`, `zoomTo`. There is no `showSea`, `traceOutline` or `showHere` verb — the seas are `revealSymbol`, the outline is `revealSymbol:outline`, and the ring belongs to `zoomTo`.
- `MIN_HOLD` 1000ms. **Only `countTo` is capped, at 5000.** Everything else is uncapped — those are pictures of the subject, and the subject is what the sentence is about.

  **Correction, recorded because the plan asserted otherwise and was wrong.** An earlier draft justified this cap by claiming an uncapped counter would balloon `HIGHLIGHT_MS` at `GrandTour.tsx:99` and relight the whole country for the whole of beats 3 and 4. That regression **cannot occur**: `HIGHLIGHT_MS` reads the module constant `HOLD.counter`, never `cue.hold`, and `highlightAllStates`/`highlightUnionTerritories` are not art verbs so they carry no hold at all. Highlight release stays fixed at 36 × 70 + 5000 = 7520ms regardless of what this cap is set to.

  The cap is still correct, but for a smaller reason: it bounds the counter **disc** itself. Uncapped, the derived holds are 13.31s on tour.03 and 15.11s on tour.04 — a spinning number parked on screen for essentially the entire beat, long after the sentence has moved on. Five seconds is enough to read "28".
- `Cue` gains `hold?: number`. `OverlayRenderer` becomes `(arg, hold) => ReactNode`. Every effect takes a `hold` prop **defaulting to its current constant**, so the draft-voice path and every single-effect test keep working.

### Task 4: Fit the map on the screen

**Files:**
- Modify: `src/tour/grandTour.css`, `src/tour/tourStage.css`, `src/map/map.css`, `src/map/MapStage.tsx`, `scripts/lib/mapPage.mjs`, `src/map/MapStage.test.tsx`
- Modify: `scripts/tour-strip.mjs` (**already done and verified by the diagnosis — confirm it is in the tree**)

**The defect.** `.tour-stage` is `flex: 1 1 auto` of a full-height column, `.map` is `100%/100%` of that, and `svg.base` letterboxes India into the **whole viewport** — including the strip the control bar covers. `Controls.css` publishes `--bar` on `:root` precisely so other things can leave room, and `grandTour.css` consumes it for the peacock, the credit, the words and the button. **The map is the one element on screen that does not know the bar exists.**

Measured: iPad Air 11 in Safari portrait, 28.2px of the southern tip behind the bar; with the tab bar showing, 48.2px; in landscape, **120px — the entire bar height, about 21% of the country** — with Kashmir clipped at the top as well.

**Why the gate said "no collisions":** three blind spots, the first decisive. It has 16 collision clauses and **not one mentions the map**. Its device list is 2011 iPad point sizes that no iPad in Safari ever receives. And `768x1024`, the one portrait size tested, is a fluke — the map bottom lands at y=903.6 against a bar top of y=904.0, clearing by **0.4px**. Proof the first is the real failure: the gate already runs `1024x768`, where 120px of India is behind the bar, and reported clean.

**The fix**, prototyped and measured clean at every iPad viewport:

1. `grandTour.css`, in `.india`, beside the existing `--floor`:
   `--say-lines: 5; --say-lane: calc(var(--say-lines) * 1.45 * var(--text) + 20px); --map-floor: calc(var(--floor) + var(--say-lane));`
   plus `@media (min-width: 792px) { .india { --say-lines: 4 } }`.
   The lane is **fixed per breakpoint, not per beat** — which answers the objection the existing comment raises, that the map would otherwise rescale four times a minute. Measured line counts: stage under 601px → 5 lines, 601–735px → 4, 736px and up → 3. Both values carry one line of headroom.

2. `tourStage.css`: frame the map **and the art together**, because `effects.css` requires `.map` and `.tour-overlay` to be the same box or the Ganga, the Himalayas and the three seas stop landing on the geography:
   `.tour-stage > .map, .tour-stage > .tour-overlay { position: absolute; inset: 0 0 var(--map-floor) 0; width: auto; height: auto }`
   The `auto` values are required to beat `.map { width:100%; height:100% }`.

3. `.say` becomes `right: 0` instead of `right: calc(var(--mor-lane) + 12px)`. Full width takes the worst beat from 5 lines/194px down to 3 lines/124px, which is where most of the reclaimed map comes from. Then lift the peacock clear by adding `var(--say-lane)` to `--mor-floor`. **It is defined three times** — `grandTour.css:33`, `:199` and `:212` (the last adds the play button's height). All three need it; updating one and missing two puts Mor over the words at some breakpoints and not others.

4. **Move the credit out of `.map`.** `.map` keeps `overflow: hidden` — it is the clip for the camera's 10.4× flight and the clip must be at the new frame — but `.credit` is a child positioned `bottom: var(--credit-floor)`, so framing `.map` drags the credit 148.9px up into the middle of the country. Render it as a sibling inside `.tour-stage`, move the `.map .credit` selector in `map.css` accordingly, and mirror the change in the probe shell so the two cannot drift.

   **Do not instead subtract `--say-lane` from `--credit-floor`.** It is one line and it looks equivalent, but it silently redefines that variable from "height above the viewport bottom" — which is what `map.css:129` documents and what the non-tour India screen relies on — to "height above the map's bottom edge". Two coordinate systems behind one name, and at the wider breakpoints the value goes negative and drops the credit into the words.

### Task 5: Make the islands exist

**Files:**
- Modify: `scripts/build-map.mjs`, `src/map/hitLayer.ts`, `src/map/map.css`, `scripts/lib/mapPage.mjs`
- Test: `scripts/build-map.test.mjs`

**The defect, in two layers.**

*The build deletes them.* One global `-simplify visvalingam percentage=2% keep-shapes` runs over all 36 features. `keep-shapes` protects a **feature** from vanishing, not its rings, and a single area threshold sized for Rajasthan annihilates atolls. The source has 35 Lakshadweep islands (1,731 points) and 220 Andaman islands (112,114 points); `geo.json` ships 4 rings/12 points and 52 rings/727 points. **31 of 35 and 168 of 220 are gone.** The Lakshadweep survivors are literal three-point triangles.

*What survives is painted over by its own stroke.* Every path is stroked in `--land-edge`, which is `var(--paper)` — the same cream as the background — at 1.5 non-scaling px, eroding 1.21 viewBox units off every edge. All four Lakshadweep rings are 0.9–1.3 units on their narrow axis, **narrower than their own stroke**, so they contribute no land pixels whatsoever. 37 of the 52 Andaman rings fail the same test.

Measured at 1024×768: deleting Lakshadweep from the data entirely changes **13 pixels**, maximum 1/255 on any channel. Not one pixel reaches even half the land colour.

**5a — rebuild the data.** Replace the global simplification with a **per-place simplification to a screen-space tolerance**, the way `build-hitlayer.mjs` already binary-searches to a point budget. Simplifying in projected viewBox units to a stated error (0.3 units = 0.19px at the home view) keeps every ring, instead of applying one lon/lat area threshold to both Rajasthan and an atoll. Without this the islands stay deleted no matter how they are painted, and a camera flight to either arrives at three-point triangles.

**5b — a minimum-dimension stroke.** Emit `data-islands` from the build for every place whose `neighbours` array is empty — exactly Andaman & Nicobar and Lakshadweep, **derived not listed**, in the spirit of `needsPin`. Then three CSS rules stroking those paths in `--land` (not `--land-edge`) at width 4, with `.lit` variants so a lit island territory changes colour rather than staying beige.

This is the standard cartographic minimum-dimension rule — the same one that draws rivers wider than they are. Positions stay exact, relative sizes are preserved above the floor, only widths are inflated by a constant. And because it inherits `non-scaling-stroke`, the exaggeration is a fixed number of CSS pixels at every camera scale, so **it shrinks away as the camera flies in and the true coastline emerges.**

Rejected, with reasons: a magnified inset box needs a duplicated transformed copy plus its own hit rect, and would blow up 12× with the camera or sit stale over a zoomed view. A minimum-radius circular marker discards the island count and shape — Andaman's 52 islands become one dot. Scaling the group in place has nowhere to go: Andaman's bbox already touches y=1100.

- [ ] **Step 1: Write the failing test.** Assert every place has more rings than today for the two island territories; assert the narrowest ring of each exceeds the rendered stroke width; assert `data-islands` is present on exactly the places with no neighbours and derived from the data. Add a pixel test: rendering with and without Lakshadweep must differ by a meaningful number of fully-painted pixels, not 13.

- [ ] **Step 2: Implement 5a, regenerate, and re-run everything downstream** — `hit.json`, the geo-art, the `northernBound` assertion, both probes. `geo.json` will grow; report by how much.

- [ ] **Step 3: Implement 5b.**

- [ ] **Step 4: Look at it.** Render the map and confirm both territories are visibly present at the home view, and that flying to Andaman & Nicobar reveals real islands rather than triangles. ### Task 7: Re-render the narration with prosodic continuity

**Files:**
- Modify: `scripts/tts.mjs`, `scripts/tts-providers/elevenlabs.mjs`, `scripts/tts-providers/say.mjs`, `scripts/lib/cache.mjs`
- Test: `scripts/tts.test.mjs`, `scripts/tts-providers/elevenlabs.test.mjs`

**This task runs last in Phase 1, and the ordering is a hard constraint.** Land Task 3 first. The cue-anchoring argument for re-render safety is sound — cues address word indices, so timestamps moving is harmless — but it covers **cues only**. It does not cover hand-tuned millisecond constants, three of which are already provably stale against the current audio. Re-render before Task 3 and you silently re-break the art timing you just fixed.

**The defect.** `synth()` posts `{ text, model_id, voice_settings }` and nothing else. The fourteen tour beats are one continuous four-minute read split into fourteen unconditioned requests, rendered through a pool of 4 in queue order — so consecutive beats are frequently generated concurrently by unrelated requests. There is no shared prosodic context, and pitch, pace and energy drift between them.

**Verified against current docs:** the `/with-timestamps` endpoint accepts `previous_text`, `next_text`, `previous_request_ids` and `next_request_ids`; the id arrays cap at 3; ids are valid about 2 hours; a chain is inherently serial, because conditioning requires the previous request to have "processed completely"; `previous_text` is **ignored** when `previous_request_ids` is also sent; works on `eleven_multilingual_v2`.

**The design:**

- **Runs.** Replace `collectLines()` with `collectRuns()` returning `[{ id, lines }]`. `content/tour.json`'s `beats` array is the **only** multi-line run — 14 lines in authored order, because `GrandTour` chains them on `onEnd`. Every place intro, each of the four card lines, each of the five landmark lines and every UI line is a **run of one**: nothing plays them consecutively, and conditioning a card line on the intro would make an independently-tapped line open like the continuation of a sentence the child never heard. **Derive the grouping from the content** — `tour.json` is the only file declaring an ordered sequence — so a future continuous sequence declares its own run. *This is the part that matters for the state screens: when Plan 4 adds 32 places, they inherit runs-of-one for free, and if a place ever plays its five landmarks continuously it declares that itself.*
- **Continuity, forward pass only.** Send `previous_request_ids` (up to 3 preceding lines of the same run, most recent last) and `next_text` (the next line's raw text). Do **not** send `previous_text` alongside the ids — it is ignored. Do **not** build `next_request_ids` — it needs ids that do not exist yet and it suppresses `next_text`.
- **Serial within a run, parallel across runs.** Move the pool of 4 from lines to runs. With one 14-line run and 59 one-line runs, concurrency stays at 4 and the tour becomes the critical path — about a minute.
- **Chain the cache key along the run:** `key_i = sha256(signature + text_i + '|' + nextText_i + '|' + key_{i-1})`. Clip N's audio is now a function of its whole run prefix, so keying on its own text alone would keep stale audio conditioned on an edited neighbour. **Say this plainly in the preflight:** the 14 beats are one atomic unit, so editing beat 3 re-renders beats 3 through 14. Worst case (editing beat 1) is 2,428 characters, **$0.24**. Keep the stitching marker out of the single-line runs' keys so the other 9,185 characters stay cached.
- **Run-aware `--only` and `--force`.** `--only=tour.07` must either error or widen to the whole run: rendering one member in isolation reintroduces exactly the seam being fixed. Store `{ key, requestId, renderedAt }`; on resume reuse ids only if under 2 hours old, otherwise restart the run from its first line — $0.24 buys a tour with no joint in it.

- [ ] **Step 0 (do this first): close the `tts:draft` footgun.**

  Discovered during Task 3 and deliberately deferred to here, because this task is already rewriting the cache key. **The hazard is live until it is fixed.** `npm run tts:draft` runs `--provider=say`; the cache key folds in the provider signature, so every one of the 73 lines misses, and the `--yes` confirmation gate at `tts.mjs:95-105` sits **inside `if (providerName === 'elevenlabs')`** — so there is no prompt at all. It overwrites every paid clip with the macOS robot voice, and because `say` returns no alignment, `estimateTimings` also rewrites every `starts[]` array, destroying the baseline that would have proved the damage.

  The fix is **not** "prompt whenever anything renders": `--force` is a user explicitly asking to re-render, and several existing tests depend on it working unprompted. The invariant to enforce is narrower — *refuse to silently overwrite clips that a different provider produced*. Persist the provider signature alongside the cache (a sidecar key, e.g. `__provider`; verify nothing iterates the cache treating every key as a line id), and when the stored signature differs from the current one and clips already exist on disk, require `--yes`. First run has no stored signature and must not prompt.

  Test it: a run that changes provider with existing clips exits without rendering and without `--yes`; the same run with `--yes` proceeds; `--force` on an unchanged provider is unaffected; a fresh tree prompts for nothing.
